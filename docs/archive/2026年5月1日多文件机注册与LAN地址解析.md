# 2026年5月1日多文件机注册与 LAN 地址解析（含信令/数据流与安全原则）

本文档把**产品架构结论**与**本仓库已落地实现**写在一起，避免「讨论一套、代码另一套」。实现细节以代码与迁移为准；原则性要求以本节前五章为准。

---

## 一、信令与数据流分离 —— 结论与边界

### 1.1 结论：**行**

对图片/视频素材库，这是经典做法：

| 层级 | 职责 |
|------|------|
| **ECS（信令层）** | 会话、鉴权、权限、素材与文件元数据、**LAN 根地址解析结果**、**票据签发**、审计与 `nas_jobs` 排队；**不转发用户文件二进制流**（不把 API 机当大文件网关）。 |
| **NAS 侧 / 文件机 HTTP** | 只服务「**已授权、短时、与路径绑定**」的请求（票据或等价校验），**读盘 / 写盘**；可多台水平扩展。 |

**好处**：ECS 带宽与磁盘压力小、大文件走就近链路、扩容主要扩文件机与出口，而不是扩 API 机去扛字节流。

### 1.2 必须写清的**例外路径**（否则「永不转发二进制」会与运维/合规打架）

若存在以下任一情况，应在架构图与运维手册中**单独标注为「例外通道」**，与「默认直连文件机」并列说明，避免口头承诺「ECS 绝不碰文件」：

- **公网用户完全碰不到内网 NAS**：仍可能需要 **ECS 或边缘缓存** 上的 `prepare_download` 回传缓存（本仓库已有该路径），或专用 CDN/反代；这不是失败，是**网络模型不同**下的合法分支。
- **合规要求集中留痕 / 集中病毒扫描**：文件可能必须先落指定缓冲区再分发，与「浏览器直连 NAS」冲突时，应用显式产品开关控制走哪条链。

**本仓库现状**：默认主推 **局域网票据 + 文件机 HTTP**；`prepare_download` 等仍属**信令驱动的异步数据面**，是否经 ECS 磁盘缓存由部署与权限决定，**不属于「ECS 纯信令」的绝对化承诺范围**。

## 二、地址同步（`current_file_url` / base URL）—— 结论与工程要求

### 2.1 结论：**行**；动态出口（DDNS/穿透）下，**上报 + ECS 侧持久化「当前可用 base」**是合理设计。

### 2.2 **禁止**依赖「ECS 进程内存里唯一真源」

| 场景 | 要求 |
|------|------|
| **单台 ECS** | 若不用 DB，仅用内存，重启即丢；仍须 **TTL + 心跳超时**，前端/API 在节点全过期时应得到 **「暂无直连」** 语义，而不是陈旧 URL。 |
| **多台 ECS / 水平扩** | **必须**使用 **共享存储**（本仓库采用 **PostgreSQL 表 `nas_file_service_nodes`**）；或 Redis + 版本号；**不得**各实例各记一份内存。 |

**本仓库已落实**：注册表在 **PostgreSQL**；解析时用 **`last_seen_at` + `FILE_SERVICE_NODE_STALE_SECONDS`（默认 120s）** 判定是否参与选路，等价于「约 2～3 个上报周期未上报则视为不可用」的工程化版本。

### 2.3 建议的上报字段语义（与实现对照）

| 讨论中的建议 | 本仓库现状 | 后续可增强 |
|--------------|------------|------------|
| **base_url**（上传/下载根，非每条文件 full URL） | 已实现：`lan_upload_base_url`、`lan_download_base_url` 两根。 | 如需「单根」，可由运维在两侧填同一值。 |
| **status、last_seen_at** | 已实现：`status`、`last_seen_at`。 | `draining` / `offline` 已预留枚举。 |
| **version / nonce（防乱序覆盖）** | 未实现；当前以 **`last_seen_at` 最新优先** 选节点。 | 可在心跳体增加 `reported_at` 或单调版本，服务端拒绝回拨。 |
| **capabilities（仅上传/仅下载/分片上限）** | 未实现。 | 可 JSON 字段扩展，解析时过滤节点。 |

### 2.4 前端拿文件时：两种等价形态（二选一即可）

- **ECS 拼好完整 URL**：`{resolved_download_base}/download?ticket=...`（当前实现），**票据与 `material_id` / `file_path` / scope 绑定**，由 NAS 校验 HMAC。
- 或 **只返回 base + 票据**，由前端拼接（需统一路径规则）；关键是 **Token 与对象路径绑定**，禁止「裸路径无票访问」。

## 三、安全与威胁模型（要求级，不替代具体渗透测试）

以下与现有 **HMAC 票据 + `exp`** 模型**同一套规范**延续，避免「第二套 Token」并行。

| 点 | 实现语义（要求） |
|----|------------------|
| **短时 Token** | 短时 **HMAC 票据**（或未来 JWT）；载荷绑定 **`material_id` / `file_id` 或 `file_path` / `scope`（read\|write\|thumbnail_direct\|lan_upload）**、**`exp`**；NAS 只信 **与 ECS 一致的 `DOWNLOAD_TICKET_SECRET`**（多 ECS 必须同配或迁移到非对称 JWKS）。 |
| **仅允许带 Token** | 文件机 HTTP：**默认 deny**；仅放行带票路径 + **`/health`** 等白名单；推荐 **Nginx `auth_request`** 或应用内中间件二选一。 |
| **禁目录浏览、后缀白名单、限速** | 运维在 Nginx/网关侧落实；限速区分 **预览小流量** 与 **整文件下载**（避免误伤缩略图）。 |
| **额外建议** | 公网穿透场景 **HTTPS**；**极短 TTL** 或一次性消费（当前多为短 TTL + 路径绑定）；**日志不落 ticket 明文**；CORS/Referer 按需收紧。 |
| **密钥轮换** | 轮换 `DOWNLOAD_TICKET_SECRET` 需 **全 ECS、文件机侧校验配置同步**，并有回滚窗口说明。 |

**本仓库代码范围**：票据算法与签发逻辑在 ECS；**Nginx 限速、HTTPS 终止、目录浏览** 在部署仓库/运维手册中约定，**不在应用代码内强制**。

## 四、与现状的衔接（避免重复造轮子）

- 已有 **局域网票据**、NAS 上 **upload/download HTTP**、**`nas_jobs` worker 轮询**、**`prepare_download` 缓存链**。
- 本次演进是：把「写死在 `.env` 的 `LAN_*_BASE_URL`」扩展为 **「文件机心跳写入 DB + 仍由 ECS 签票」**，无注册或全过期时 **自动回退 `.env`**，兼容旧部署。
- **反向代理**：若公网入口 Nginx 对 API 做了 `proxy_pass`，须文档写明 **大文件不经由该路径转发**（直连票走文件机域名/端口），避免运维误配把文件流又兜回 ECS。

## 五、产品 / 运维前置决策（未定案则易返工）

建议在评审纪要中逐条勾选：

1. **用户网络模型**：仅办公室局域网可连文件机，还是公网/家庭也要直连？后者几乎强制 **HTTPS + 更强滥用监控 + 更短 TTL**。
2. **多 NAS / 多地域**：ECS 返回的应是 **「该素材所属 `storage_pool_id` 对应的文件机 base」**，而不是全局单一 URL（本仓库已用 **`materials.storage_pool_id`** 预留；上传票当前仍绑 **默认池**，见下文实现章）。
3. **上传完整性**：大文件直传文件机后，**SHA256 / 病毒扫描 / 入库** 仍由 **ECS 信令 + `nas_jobs` 异步** 对齐（与现有 ingest 模型一致）。
4. **地址切换瞬间**：长下载可失败，由 **前端用新 ticket 重试**（一般可接受）；须在 UI/文档中写明。

## 六、本仓库已落地实现（对照第二节）

- **表**：`nas_file_service_nodes`；**素材字段**：`materials.storage_pool_id`（默认 `default`）。
- **心跳**：`POST /nas-jobs/file-service/heartbeat`（`X-NAS-Client-Token` 与 poll 同源）。
- **运维列表**：`GET /nas-jobs/file-service-nodes`（超管 / 素材管理员）。
- **解析**：`resolve_lan_base_urls(db, pool_id)` → 用于 **缩略图 LAN、下载票 LAN、上传票 LAN**（上传票当前为 **`_lan_roots_for_default_pool`**，与「网页入口默认落默认池」一致，多池上传可后续扩展）。
- **前端**：`GET /nas-jobs/client-status` 增加 `file_service_*` 字段；素材库页展示池与健康节点数。
- **脚本**：`nas-client/report-file-service-heartbeat.ps1`。
- **迁移**：Alembic **`20260501_0013`**。

部署：`cd backend && alembic upgrade head`。  
若执行时报 **`connection timeout` / `localhost:5432`**，说明本机 **PostgreSQL 未启动或 `DATABASE_URL` 不可达**，与迁移脚本本身无关；先起库或改用可达的 `DATABASE_URL` 再跑。

### 6.1 存储池与入库、运维修改

- **LAN 入库** `POST /materials/ingest-from-nas`：请求体可选 **`storage_pool_id`**；缺省使用 **`DEFAULT_STORAGE_POOL_ID`**。校验规则：1～64 字符，首尾为字母数字，中间可为 `._-`。
- **文件机 `download_server.py`**：若设置环境变量 **`NAS_STORAGE_POOL_ID`**，写入 NAS 后的入库 JSON 会带上该字段（与命令行 `lan_uploader.py --storage-pool-id` 等价）。
- **管理员改池**：`PATCH /materials/{material_id}/storage-pool`，Body `{"storage_pool_id":"pool-a"}`，需权限 **`asset.edit_all`**（多池迁移用）。
- **一键启动**：`start-nas-direct-services.ps1` 可选参数 **`-FileServiceLanBase`**（及 `-ApiBaseUrl`、`-FileServicePoolId`、`-FileServiceNodeId`）：非空时额外打开第 4 个窗口跑 **`report-file-service-heartbeat.ps1`**，向 ECS 注册当前 LAN HTTP 根地址。

### 6.2 心跳 JSON 示例

```json
{
  "pool_id": "default",
  "node_id": "OFFICE-FILE-01",
  "lan_upload_base_url": "http://192.168.1.10:9001",
  "lan_download_base_url": "http://192.168.1.10:9001",
  "status": "online"
}
```

`pool_id` 可省略，则使用环境变量 **`DEFAULT_STORAGE_POOL_ID`**（默认 `default`）。

### 6.3 环境变量

| 变量 | 含义 |
|------|------|
| `DEFAULT_STORAGE_POOL_ID` | 默认池 ID |
| `FILE_SERVICE_NODE_STALE_SECONDS` | 未心跳超过该秒数则不参与选路（默认 120） |
| `LAN_UPLOAD_BASE_URL` / `LAN_DOWNLOAD_BASE_URL` | 无可用注册节点时的回退 |

### 6.4 LAN 根地址解析（实现规则）

1. 取素材的 `storage_pool_id`（缺省 `default`）。
2. 在该池中取 `status=online` 且 `last_seen_at` 未超出 stale 的节点，按 **`last_seen_at` 降序、`node_id` 升序** 取第一条。
3. 若无可用节点，回退 **`.env` 的 `LAN_*`**。

**同池多机**：若各节点 URL 不同，当前实现会选 **最近心跳**；运维建议同池上报 **同一 VIP/SLB DNS**。

### 6.5 变更文件摘要（便于 Code Review）

`backend/.../nas_file_service_node.py`、`file_service_registry_service.py`、`nas_jobs.py`、`materials.py`（含 **`PATCH .../storage-pool`**）、`material_service.py`（池校验与入库写池）、`material.py`、`serialize_material`、`schemas/material.py` / `nas_job.py`、`config.py`、Alembic `20260501_0013`、`nas-client/report-file-service-heartbeat.ps1`、`download_server.py`（`NAS_STORAGE_POOL_ID`）、`lan_uploader.py`、`start-nas-direct-services.ps1`、前端素材库 `NasClientStatus` 与提示条。

## 八、文件机侧：便捷切换 ECS API 地址（`NAS_API_BASE_URL`）

文件机上的 **`run-worker.ps1` / `run-download-server.ps1` / `report-file-service-heartbeat.ps1`** 会连到 **ECS 上的 FastAPI**（默认端口 **8000**）。解析顺序为：

1. 命令行 **`-ApiBaseUrl "http://新ECS公网IP:8000"`**（临时、优先级最高）  
2. **`nas-client/ecs-api-url.txt`**：第一行非空、非 `#` 开头的 URL（建议从 **`ecs-api-url.txt.example`** 复制改名；该文件已 **gitignore**，每台文件机各写各的）  
3. 当前会话环境变量 **`NAS_API_BASE_URL`**  
4. 以上皆无则回退 **`http://127.0.0.1:8000`**（请用 1 或 2 显式配置生产地址）

**换新 ECS**：在文件机上改 **`ecs-api-url.txt` 一行地址**，保存后 **重启** worker、LAN 服务、心跳脚本即可。

**两台 ECS 都要用**：一个 worker 进程**同一时间只连一个** API 基址。常见做法：  
- **同一套库、双机热备 / SLB**：在 `ecs-api-url.txt` 里写 **VIP 或统一 DNS**，不要来回改两台 IP。  
- **两套独立环境**（两套库）：开 **两个 PowerShell**，分别 **`-ApiBaseUrl http://ECS-A:8000`** 与 **`-ApiBaseUrl http://ECS-B:8000`**（或准备两份 `nas-client` 目录各放自己的 `ecs-api-url.txt`）。

**浏览器 / 办公网访问**：另需与 ECS 配套的 **`frontend/.env.local`** 里 **`NEXT_PUBLIC_API_BASE_URL`**（以及 LAN 相关项），见 `2026年4月26日更新发布流程.md`。

### 8.1 仍 401：自检脚本与空白字符

在文件机 **`nas-client`** 目录执行 **`.\verify-nas-token.ps1`**：对 **`ecs-api-url.txt` 解析出的 API** 发一次 **`GET /nas-jobs/poll`**，打印 **HTTP 状态** 与 **Token 字符长度**（可与 ECS 上 `.env` 中值长度对照）。  
客户端与 ECS 均已对 **`NAS_CLIENT_TOKEN`** 做 **`strip()` / UTF-8 BOM 去除**，避免 **`nas-client-token.txt` CRLF、行尾空格** 导致不一致。
