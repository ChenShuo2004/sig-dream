## 4 月：立项与第一阶段上线

### 4 月 25 日：先做素材，再做工作流

最初的设想是「工作流编排台」，但立项当天就调整了顺序：**先把素材资产管理做稳，工作流画布之后再接**。理由是团队每天真正卡住的是素材的上传、打标、查找和下载，工作流节点最终也要调用这些能力。

第一阶段拆成 11 步，必须按顺序推进：项目骨架 → 用户与权限 → 标签体系 → 分片上传 → 素材入库 → 搜索与详情 → 下载与使用记录 → 回收站 → NAS Client → FFmpeg 派生 → 前端整合。最小闭环是：登录 → 上传视频 → 选标签 → 分片上传 → 入库 → 生成缩略图 → 搜索 → 下载。

同一天完成了部署方案：阿里云 ECS 上不用 Docker、直接按 IP 和端口跑 FastAPI + Next.js，用 Cursor 连接 GitHub 推送代码。数据库迁移从 `20260425_0001_create_workflows` 开始。

### 4 月 28 日 – 4 月 30 日：素材库闭环与权限统一

- **素材库页面闭环**：列表、筛选、预览、下载、收录、加入未整理，分阶段做完。
- **上传与下载全链路**：明确 **ECS 只负责鉴权、票据和元数据，不搬大文件**；大文件走文件机，公网下载有 ECS 缓存兜底。上传状态语义写死，不允许「看起来上传完了其实没入库」。
- **系统设置**：用户、角色、权限点、安全策略、上传限制、回收站规则。
- **权限统一改造**（4 月 30 日）：`/auth/me` 返回权限点列表，前端按权限点控制按钮；业务代码不再写死角色名，统一走 `ensure_permission`。
- **NAS 扫描重建**：写好从 NAS 文件反推数据库元数据的脚本模板，防止数据库丢失后素材找不回来。
- **术语对齐**：开始维护术语对齐记录，把口语说法映射到权限点、接口和数据模型，之后一直持续追加。

## 5 月：局域网传输、换服务器与桌面端

### 5 月 1 日：局域网直传的三个坑

这一天集中解决了文件机（办公室 NAS 旁的电脑）相关的问题：

1. **大文件上传显示完成，NAS 上却是 0 字节。** 原因有三个：文件机把整个 multipart 读进内存；上传票据没有绑定文件大小；前端收到 HTTP 2xx 就标记完成。修复后，票据带上 `file_size`，文件机流式落盘并校验大小，前端比对返回的大小，不一致就不算完成。
2. **长时间没有缩略图。** 根因通常是文件机上没有常驻的 poll 进程。确定架构：缩略图只在局域网侧用 ffmpeg 生成，ECS 只排队和落库；文件机上跑两个进程，全量 worker 和缩略图专服分开。
3. **多台文件机。** 信令和数据流分离：ECS 只下发票据和地址，文件内容直接在浏览器和文件机之间传。文件机定期上报心跳和可用地址（迁移 `0013`、`0014`）。

### 5 月 3 日 – 5 月 9 日：换到新 ECS

迁移到新服务器的过程中沉淀了一整套运维文档：

- **双密钥**：本机到 ECS、ECS 到 GitHub 各用一把 SSH 密钥，按命令逐步配置。
- **PostgreSQL 与 `.env`**：在新 ECS 上装数据库并写好后端配置。
- **数据库备份**：ECS 每天自动备份，文件机定时拉取到本地保存。
- **操作日志清理**：数据库备份涨到约 592 MB，排查发现 `operation_logs` 约 174 万行、占了备份的绝大部分，于是写了按类型分析与清理的步骤。
- **全新 ECS 的部署顺序**：必须**先首次发布再导入数据库**，否则远端还没有 `backend/.env` 和虚拟环境，导入会失败。

## 经验与教训

1. **服务器不搬大文件。** ECS 只做鉴权、票据、元数据和任务编排，大文件在浏览器和局域网文件机之间直传。这条原则贯穿了上传、下载、缩略图、内容识别和翻唱。
2. **「上传完成」必须有证据。** 0 字节事件之后，上传是否完成以文件机落盘后的大小校验为准，而不是 HTTP 状态码。
3. **后台任务要有常驻进程。** 缩略图、预览、内容识别都依赖文件机持续 poll；「没有缩略图」首先查 worker 是否在跑。
4. **权限按权限点控制，不写死角色。** 新功能只需新增权限点并在系统设置里分配。
5. **密钥不进仓库，也不进安装包。** 仓库只保留 `*.example` 模板；安装包里的任何文件都应当可以公开。
6. **全新环境要从零验证。** 开源前用全新数据库从头跑一遍，才发现了首次登录 500 的问题。
